# Angular + C#/.NET Coding Pattern Enforcement Skill

## Objective

Create a reusable coding-governance skill for VS Code Copilot for an existing **Angular + C#/.NET application**.

The purpose of this skill is to ensure that whenever Copilot creates, modifies, fixes, or refactors code, it follows the **existing coding patterns and architecture of the repository**.

The skill must behave like a senior engineer joining an existing enterprise codebase.

### Primary principle

> **Existing project patterns are the source of truth. Do not introduce a new pattern when an equivalent established pattern already exists.**

Do not blindly apply generic Angular, C#, .NET, or "modern best practice" patterns if the existing project uses a different established approach.

# 2. Existing Pattern Discovery

For every important pattern, find actual examples in the repository.

For example:

```text
Pattern:
Angular API calls are handled through dedicated services.

Examples:
src/app/services/user.service.ts
src/app/services/order.service.ts
src/app/services/product.service.ts

Rule:
Components must not directly implement HTTP API calls.

Confidence:
High
```

For C#:

```text
Pattern:
Controllers delegate business logic to application services.

Examples:
UserController.cs
OrderController.cs
ProductController.cs

Rule:
Controllers should not contain business logic.

Confidence:
High
```

The skill must prefer patterns repeated across multiple files.

Do not create mandatory rules from a single unusual implementation.

# 3. Angular Coding Rules

## Components

Determine the project's existing conventions for:

* Component naming
* File naming
* Component structure
* Constructor vs `inject()`
* Inputs
* Outputs
* Signals
* Observables
* Lifecycle hooks
* Change detection
* Template organization

When creating a component, copy the structure of the closest existing component.

---

## Angular Services

Determine how existing services handle:

* HTTP requests
* API URLs
* Headers
* Authentication
* Error handling
* RxJS operators
* Mapping
* Caching
* Loading state

If the repository has an established service pattern:

> Always follow it.

Do not introduce another HTTP abstraction.

---

## RxJS

Analyze existing usage.

Determine whether the project prefers:

* `Observable`
* `Subject`
* `BehaviorSubject`
* Signals
* `async` pipe
* `subscribe()`
* `switchMap`
* `mergeMap`
* `concatMap`
* `forkJoin`
* `combineLatest`
* `catchError`
* `finalize`
* `shareReplay`

Do not introduce a different reactive approach without a reason.

---

## Angular Forms

Identify whether the project uses:

* Reactive Forms
* Template-driven Forms
* FormBuilder
* Typed forms
* Custom validators
* Shared validators

New forms must follow the existing project pattern.

---

## Angular Routing

Follow existing patterns for:

* Routes
* Lazy loading
* Guards
* Resolvers
* Route parameters
* Query parameters
* Navigation

Do not create a new routing architecture.

---

## Angular State Management

Detect whether the project uses:

* Services
* RxJS state
* NgRx
* Signals
* ComponentStore
* Another state library

Use the existing approach.

Do not introduce a new state-management library for a feature unless explicitly requested.

Maintain a separate set of rules derived from recurring manager/reviewer feedback.

Example:

```text
REVIEW-001

Category:
Angular Architecture

Rule:
Do not call HTTP APIs directly from components.

Required:
Use the existing Angular service layer.

Source:
Code review feedback
```

Example:

```text
REVIEW-002

Category:
C# Architecture

Rule:
Controllers must not contain business logic.

Required:
Delegate business logic to the existing application/service layer.
```

Example:

```text
REVIEW-003

Category:
Logging

Rule:
Do not use console.log for application logging.

Required:
Use the existing project logging mechanism.
```

Reviewer rules should be applied to future changes.

# 15. Reviewer Feedback Learning

When the user provides a review comment such as:

> "Don't create another helper. Use the existing utility."

Convert it into a reusable rule:

```text
REVIEW-004

Rule:
Before creating a new helper or utility, search for an existing equivalent.

Action:
Reuse or extend the existing utility where appropriate.
```

When the user provides a recurring review correction, treat it as a candidate permanent project rule.

Do not automatically create a rule from a one-off contextual comment unless explicitly requested.

# 16. Pattern Violation Detection

After writing code, compare it against the discovered patterns.

Example:

```text
⚠ Pattern Violation

Existing pattern:
Angular components use dedicated services for API communication.

Reference:
src/app/services/customer.service.ts

New code:
CustomerComponent directly calls HttpClient.

Recommendation:
Move the API call to the existing service pattern.
```

C# example:

```text
⚠ Pattern Violation

Existing pattern:
Controllers delegate business logic to application services.

New code:
Business logic was added directly to the controller.

Recommendation:
Move the logic to the existing service layer.
```

# 17. Pattern Drift Detection

Detect when new code introduces:

* Different architecture
* Different naming
* Different folder structure
* Different HTTP approach
* Different error handling
* Different logging
* Different state management
* Duplicate utilities
* Duplicate services
* Duplicate models
* Unnecessary dependencies

Report:

```text
⚠ Pattern Drift Detected

Existing approach:
<existing pattern>

New approach:
<new pattern>

Existing references:
<files>

Recommendation:
Follow the existing repository pattern.
```

---

# 18. Avoid Unnecessary Refactoring

When implementing a feature:

DO:

```text
Existing pattern
+
Minimal required changes
+
Feature implementation
+
Tests
```

DO NOT automatically do:

```text
Feature implementation
+
Architecture redesign
+
Unrelated refactoring
+
Dependency replacement
+
Code style migration
```

Only perform broader refactoring when explicitly requested.

---

# 19. Rule Confidence

Every discovered rule should have confidence:

### HIGH

Pattern appears repeatedly across the repository.

### MEDIUM

Pattern appears in a particular feature/module.

### LOW

Pattern appears only in one or two places.

Only HIGH confidence patterns should normally be treated as mandatory global rules.

---

# 20. Exceptions

Existing documented exceptions must be respected.

Example:

```text
General rule:
API calls must go through services.

Exception:
Application startup health-check is performed directly by bootstrap code.

Reason:
Required during application initialization.
```

Do not flag documented exceptions as violations.

---

# 21. Pattern Evolution

Do not assume the first discovered pattern will remain permanent.

If a newer pattern begins appearing consistently:

```text
Existing:
NgModule architecture

Emerging:
Standalone components

Evidence:
<files>
```

Report:

```text
Potential Pattern Evolution Detected

The repository appears to be gradually adopting a new pattern.

Do not automatically migrate existing code.

Use the established pattern for the current feature unless the project has explicitly adopted the new pattern.
```

---

# 22. Rule Precedence

Use this order:

```text
1. Explicit project architecture
2. Established repository pattern
3. Approved reviewer/manager rules
4. Local module pattern
5. General Angular/.NET best practices
```

If two rules conflict, do not silently choose one.

Report:

```text
⚠ Coding Rule Conflict

Existing repository pattern:
<pattern>

Reviewer rule:
<rule>

Conflict:
<description>

Action:
Clarification required before changing the architecture.
```

# Core Principle

Always think:

> "How would an existing developer in this repository implement this feature?"

Not:

> "What is the newest or theoretically best way to implement this feature?"

The generated code must look like a natural continuation of the existing Angular + C#/.NET codebase.
